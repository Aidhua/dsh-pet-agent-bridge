## 1. 技术决策复盘

### 1.1 R1：以 PC2005-cloud/dsh-pet 0.4.5 为基座（而非 Daliuq fork）——正确
- Daliuq fork 依赖的 `apiProxy`、`/api/respond`、`/api/events.mux` 在本机 DSH 0.2.2-rc.1 中零命中（断链），直接采用会不可用。
- dsh-pet 0.4.5 与官方 harness 的耦合点（petApi7340、createSessionNotify、/state/work-status）全部实测可用。决策被 E2E 结果验证。

### 1.2 伴随 bundle 而非改上游构建产物——正确
- 零构建依赖、加载即共存、卸载即回滚；M2 合并只是文件搬运。代价是与 dsh-pet 的耦合仅靠一处 6 行拦截补丁+软查找，这个耦合被控制在最小面。

### 1.3 零自绘 UI——正确
- 任务状态直接复用 dsh-pet 原生 session→workStatus 管线，省掉整条 UI 适配链路，且与宠物动画天然一致。

### 1.4 双面记忆一份存储——正确
- "聊天认识你、干活忘了你"是陪伴型 Agent 最典型的割裂；单存储双注入从数据结构上杜绝了不一致的可能。

## 2. 错误与修复（按严重度）

| # | 问题 | 根因 | 修复 | 教训 |
|---|---|---|---|---|
| 1 | DSH JSON.parse 失败 | PowerShell `-Encoding utf8` 写入带 BOM | `UTF8Encoding($false)` 重写 | Windows 上写 JSON/YAML 一律无 BOM；跨工具写文件先验编码 |
| 2 | 插件加载被拒 | bundle 双导出 `apply` | 修导出 | host 对插件形状的校验是硬约束，接入前先读加载器源码 |
| 3 | **cancel 调用 TypeError 击穿 host** | `sessionController.cancel` 是同步方法却按 Promise `.then` | 同步调用+try/catch | **API 同步/异步语义必须源码核实，不能靠猜**；这类错误直接危及进程存活，属最高优先级 |
| 4 | MSYS bash 把 `/称呼` 转成盘符路径 | MSYS 路径自动转换 | 斜杠在 Python 内拼接（`'/' + env`） | Windows+Git Bash 下所有含 `/xxx` 字面量的命令都要防转换 |
| 5 | TaskStop 后旧 host 仍答话 | Electron 子进程未随任务终止 | 决定性测试（改名 dsh-pet 目录）定位 | "看似无效"的补丁先怀疑残留进程；做决定性实验而非反复重试 |
| 6 | `/task 帮我…` 被路由为空描述 | 中文无空格整句被 split 成第一 token | 非 status/list/cancel 开头即整句提交 | 中文输入的分词假设不能照搬英文习惯 |
| 7 | 同批次 cancel 先于 submit 处理 | 轮询单遍按文件名序 | 两遍轮询（submit 先、cancel 后）+ pendingCancel | 并发入口的顺序性要显式设计，不能依赖偶然顺序 |
| 8 | E2E 中 "900/300" 混入任务文本 | 测试脚本 `--wait` 的位置参数被 join 进 text | `--max N` 显式参数 | 测试工具本身的参数设计也要过一遍脑子；幸而桥接层表现优雅（Agent 主动询问歧义） |

## 3. 过程复盘

**做得好的**：
- 分层验证策略（无模型测试先行 12+ 项，再上真实模型 E2E）让"模型调用贵且慢"的约束下缺陷发现成本最低——路由竞态、取消语义等 bug 全在无模型层修掉，真实 E2E 一次通过 4/5。
- 独立核验原则：每个"通过"都要求证据文件可脱离工具链复核（文件字节、哈希、回执 JSON），不信任中间输出。
- 隔离纪律：全程未碰正式环境，阶段 F 哈希复验把"零修改"从声明变成证据。

**待改进**：
- host 进程生命周期管理粗糙：nohup+后台任务在会话结束后进程死亡，恢复时才发现。应改用带日志文件+心跳探针的托管方式，或至少把"重启后恢复步骤"脚本化（本次 e2e_chat.py 的 token 文件机制就是补丁）。
- 429 中断与恢复：上次会话因模型限流中断在场景二，恢复依赖人工总结上下文。若当时就把 E2E 脚本落盘，恢复会更快——**长流程任务应尽早把可重复执行的驱动脚本写成文件**，而不是依赖会话内 shell 函数。
- 任务状态在 host 内存中（tasks Map），重启后 `/task status` 历史清空（pet-memory 的 taskSessionId 除外）。可考虑 results 目录重放补历史，属低优先增强。
