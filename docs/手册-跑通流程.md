# 手册：从零跑通 dsh-pet Agent Bridge（含截图素材清单）

> 用途：这是一份**可照着做的操作流水账**，也是写「养鱼保姆级教程」时的素材脚本。
> 每一步都标了【📸 截图点 Sx】，说明**拍什么、在哪拍、镜头里要有啥**，末尾有与文章章节的对应表。
> 建议顺序：先在一个**隔离环境**（独立 `DSH_HOME`）跑通全流程，再决定是否接入日常环境。

---

## 阶段 0 · 准备（5 分钟）

### 0.1 需要的东西

| 项 | 说明 | 检查命令 |
|---|---|---|
| Windows 11（已测） | Linux/macOS 未实测 | — |
| DeepSeek Harness `0.2.2-rc.1` | Agent 宿主 | `dsh --version` |
| dsh-pet `0.4.5` | 桌宠本体 | 见 0.3 |
| 一个能用的 DeepSeek 账号凭据 | 任务要真实调模型 | DSH 内登录一次 |
| 本仓库 | 桥接代码 | `git clone` |

### 0.2 建一个隔离实验目录（强烈建议）

不要一上来就动你日常在用的桌宠。单独一个 `DSH_HOME`，跑通了再迁移：

```bash
# Windows PowerShell
$env:DSH_HOME = "D:\petlab\dsh-home"     # 换成你的路径
mkdir $env:DSH_HOME
```

> DSH 的优先级是：显式配置 > `$DSH_HOME` > `~/.dsh`。设了 `DSH_HOME` 就与日常环境物理隔离。

**【📸 截图点 S1】环境自检**
- 拍什么：终端里 `dsh --version` 的输出 + `echo $env:DSH_HOME` 的路径。
- 镜头要有：版本号清晰可读（证明 0.2.2-rc.1）。
- 文章用途：教程「准备篇」的开头，给读者一个"我这边是什么环境"的基准。

### 0.3 拿到 dsh-pet 0.4.5

```bash
# 在你的 profile 下安装（profile 名按你实际的来，例如 petlab / desktop）
cd $env:DSH_HOME\profiles\<你的profile>
npm i dsh-pet@0.4.5
```

**【📸 截图点 S2】dsh-pet 落位**
- 拍什么：`node_modules/dsh-pet/package.json` 里 `"version": "0.4.5"` 那一行（编辑器截图，圈出版本号）。
- 文章用途：教程「装鱼缸」篇——告诉读者"版本必须对，0.4.5 是打过补丁验证的版本"。

## 阶段 1 · 部署桥接（10 分钟）

### 1.1 放 bundle

```bash
# 把本仓库的 src/ 整目录拷成 profile 里的一个包
cp -r dsh-pet-agent-bridge/src  $env:DSH_HOME\profiles\<profile>\node_modules\dsh-pet-task-ctl
```

### 1.2 在 profile 的 package.json 里登记

打开 `$env:DSH_HOME\profiles\<profile>\package.json`，两处各加一条：

```jsonc
{
  "dependencies": {
    "dsh-pet": "0.4.5",
    "dsh-pet-task-ctl": "file:./node_modules/dsh-pet-task-ctl"   // ← 加这条
  },
  "dsh": {
    "bundles": [
      "dsh-pet",
      "dsh-pet-task-ctl"                                          // ← 加这条
    ]
  }
}
```

> ⚠️ 用编辑器保存时选 **UTF-8 无 BOM**。带 BOM 会让 DSH 的 JSON 解析直接失败（这是踩过的坑）。

**【📸 截图点 S3】package.json 两处登记**
- 拍什么：编辑器里 `dependencies` 与 `bundles` 两段，用框标出新增的两行。
- 镜头要有：文件名（package.json）+ 两处新增行同时可见（可上下拼接）。
- 文章用途：教程「接线」篇的核心配图——读者最容易漏的就是 `bundles` 那条。

### 1.3 打 6 行拦截补丁（一条命令）

```powershell
cd $env:DSH_HOME\profiles\<profile>
node node_modules\dsh-pet-task-ctl\scripts\patch-dsh-pet.mjs apply
```

期望输出：

```
✓ 补丁已写入：…\node_modules\dsh-pet\lib\index.js
  备份：…\node_modules\dsh-pet\lib\index.js.orig-backup
  下一步：重启 DSH，进入宠物聊天框输入 /bridge 验证。
```

脚本替你做了四件事，都是手打补丁容易漏的：

| 动作 | 没它会怎样 |
|---|---|
| **版本闸**：只认 0.4.5 | 在新版上插错位置，宠物直接起不来 |
| **字节校验**：必须是原始产物 | 对着已改过的文件重复插，代码块叠两层 |
| **首次备份**：`index.js.orig-backup`（不覆盖） | 想回滚时没有干净基线 |
| **幂等**：已打过就跳过 | 手抖跑两次 |

配套三条命令：

```powershell
node node_modules\dsh-pet-task-ctl\scripts\patch-dsh-pet.mjs check    # 体检（默认命令）
node node_modules\dsh-pet-task-ctl\scripts\patch-dsh-pet.mjs revert   # 还原
node node_modules\dsh-pet-task-ctl\scripts\patch-dsh-pet.mjs --help   # 用法
```

> 手工方式依旧可用（脚本读不到目标、或想逐字核对时）：
> ```bash
> cd $env:DSH_HOME\profiles\<profile>\node_modules\dsh-pet
> cp lib/index.js lib/index.js.orig-backup
> git apply D:\path\to\dsh-pet-agent-bridge\patches\dsh-pet-0.4.5-chatwithpet.patch
> # 非 git 目录：patch -p0 < patches\dsh-pet-0.4.5-chatwithpet.patch
> ```

补丁做的事（读一遍就懂）：

```js
// [PET-BRIDGE PATCH BEGIN]
try {
  const svc = ctx.get?.call(ctx, "petTaskCtl", false) ?? ctx.petTaskCtl;
  if (svc?.handleChatCommand && text?.startsWith("/")) {
    const r = await svc.handleChatCommand(petId, text);
    if (r?.handled === true) { ……存聊天记录、让宠物说出来、返回 ok…… }
  }
} catch (e) { log.warn?.(...) }
// [PET-BRIDGE PATCH END]
```

**关键点**：`ctx.get(..., false)` 是**软查找**——桥接没加载时返回 false，原生流程照走。所以这个补丁本身是"可失败"的，不会把宠物弄坏。

**【📸 截图点 S4】补丁工具的输出**
- 拍什么：`apply` 那三行输出（写入路径 + 备份路径 + 下一步提示）。
- 文章用途：教程里"一条命令搞定"的证据；比手打 diff 更让读者安心。

**【📸 截图点 S4b】补丁块在源码里的位置**
- 拍什么：`lib/index.js` 第 7990 行附近，`[PET-BRIDGE PATCH BEGIN]` 到 `END` 的代码块（约 24 行）。
- 镜头要有：上下文的 `unknown-pet` 报错分支（让人看出插在哪个函数里）+ 补丁块本身。
- 文章用途：教程「为什么只改 6 行」——这是最能体现"轻耦合"的一张图。

> ⚠️ **升级即失效**：`npm i dsh-pet@0.4.6` 覆盖 `index.js` 后，插件在设置页依然亮着，但 `/task` 会静默不响应。升级后重跑一次 `apply`。

### 1.4 验证补丁真的生效

```bash
grep -c "PET-BRIDGE PATCH BEGIN" $env:DSH_HOME\profiles\<profile>\node_modules\dsh-pet\lib\index.js
# 期望输出：1
```

**【📸 截图点 S5】grep 计数 = 1**
- 拍什么：终端里这条命令 + 输出 `1`。
- 文章用途：教程的"自检清单"里的一条，读者可对照。

## 阶段 2 · 启动与首次冒烟（5 分钟）

### 2.1 启动

```bash
dsh --profile <profile> --no-open --port 39190
```

窗口会打印一行：

```
dsh web: http://127.0.0.1:39190/?token=xxxxxxxx
```

复制到浏览器打开 → 出现桌宠面板。

**【📸 截图点 S6】启动成功**
- 拍什么：终端里那行 `dsh web: http://127.0.0.1:39190/?token=...`（token 可打码后 4 位）。
- 文章用途：教程「开缸」篇——读者对照自己的输出。

**【📸 截图点 S7】宠物面板全景**
- 拍什么：浏览器里的桌宠面板首屏（宠物本体 + 聊天输入框）。
- 镜头要有：**聊天输入框一定要入镜**，因为后面所有命令都从这里输入。
- 文章用途：教程封面图 / 「认识你的鱼」章节。

### 2.2 三条命令确认桥接活着

依次在聊天框输入，每次回车后等回复：

| 输入 | 期望回复 |
|---|---|
| `/bridge` | 返回命令帮助列表（/task /memory /称呼 …） |
| `/task status` | "还没有任务记录。用 /task <任务描述> 交给我吧。" |
| `/memory list` | "称呼：还没告诉我…" + "偏好：暂无记录…" |

**【📸 截图点 S8】`/bridge` 帮助回复**
- 拍什么：聊天窗里你输入的 `/bridge` + 宠物返回的整段帮助文本（一屏能放下）。
- 文章用途：教程「命令速查」章节的配图——这张图读者会反复回看。

> 如果 `/bridge` 没反应、而是宠物用它的口吻回了一句无关的话 → 说明补丁没生效或 bundle 没加载。排查顺序：S5 的 grep → 重启 host → 看终端有没有 `[dsh-pet-task-ctl] task controller ready`。

**【📸 截图点 S9】启动日志四行**
- 拍什么：终端里桥接初始化的四行日志：
  ```
  [dsh-pet-task-ctl] initialized. home=...
  [dsh-pet-task-ctl] registered as dsh-pet chat memory provider
  [dsh-pet-task-ctl] petTaskCtl service provided
  [dsh-pet-task-ctl] task controller ready
  ```
- 文章用途：教程「排错」章节——这四行是"服务真的起来了"的铁证。

1. 宠物立刻回执：`已收到任务 #chat-xxxx-1…`

3. 十几秒后它汇报：关键结果 + **文件路径**

## 阶段 5 · 连续任务：工作记录 + 周报（15 分钟）

这一阶段演示**会话连续性**——第二步不需要重复告诉它文件在哪。

### 5.1 建工作记录

```
/task 在工作区创建「工作记录」文件夹，并在其中创建本周（2026年11月2日至11月8日）的工作记录文件 worklog-week.txt，内容包含本周每天完成的至少一件事。
```

### 5.2 接着补两条 + 生成周报

```
/task 在「工作记录」的 worklog-week.txt 中补充今天新完成的两件事：1）完成了桌面宠物桥接命令的回归测试；2）完成了周报生成功能验证。然后基于该文件在「工作记录」文件夹内生成周报文件 weekly-report.md，汇总本周工作。
```

注意第二句里的 **"该文件"**——它能听懂，因为它和上一条任务是同一个会话。

**【📸 截图点 S15】连续两条任务**
- 拍什么：两条 `/task` 命令 + 两次完成回复（注意回复里它主动引用了上一个任务的文件）。
- 文章用途：教程「它会记事」章节——这是区别于"每次从零开始"的 AI 的关键体验。

**【📸 截图点 S16】工作记录文件夹**
- 拍什么：资源管理器里「工作记录」文件夹，里面 `worklog-week.txt` + `weekly-report.md` 两个文件。
- 文章用途：教程「产出」章节。

**【📸 截图点 S17】周报内容**
- 拍什么：打开 `weekly-report.md`，露出**按日表格**那一段（Markdown 预览或编辑器都行）。
- 镜头要有：日期列 + 事项列，能看出 7 天连续。
- 文章用途：教程「办公场景」章节的成果图。

## 阶段 6 · 取消与异常（10 分钟）

教程里"能取消"这件事必须演示，否则读者不敢用。

### 6.1 提交一个长任务

```
/task 在工作区创建 files 文件夹，并在其中创建 8 个测试文件 t1.txt 到 t8.txt，每个文件写入不同的两行说明文字，全部创建完成后逐一回读校验。
```

### 6.2 趁它干活时取消

等 3–5 秒（看到状态变成"干活中"），立刻发：

```
/task cancel
```
→ "正在取消任务 #…"

再查：

```
/task status
```
→ "任务 #…：已取消"

**【📸 截图点 S18】取消全过程**
- 拍什么：三段连续对话（提交 → cancel → status 显示"已取消"）。
- 文章用途：教程「止损」章节——一图讲完"能反悔"。

### 6.3 确认没有半成品

```bash
dir $env:DSH_HOME\dsh-pet-task-ctl\workspaces\pet-main
```
→ 不应出现 `files` 文件夹（任务在创建前就被中断）。

### 6.4 取消后还能继续用

```
/task 在工作区创建 cancel-ok.txt，内容为：取消后会话复用验证成功。
```

**【📸 截图点 S19】取消后继续**
- 拍什么：取消后新任务正常完成的回复 + 它主动提到"上次那个被取消的任务"（如果出现，一并截，很有说服力）。
- 文章用途：教程「不炸缸」章节——证明取消不会把鱼搞坏。

## 附：常见问题速查

| 现象 | 原因 | 处理 |
|---|---|---|
| `/bridge` 被当普通聊天 | 补丁未生效 / bundle 未加载 | 查 S5 grep；看 S9 四行日志；确认 `bundles` 里有 `dsh-pet-task-ctl` |
| 启动就报 JSON 解析错 | package.json 存成了带 BOM 的 UTF-8 | 用无 BOM 另存，或 `UTF8Encoding($false)`（PowerShell） |
| 任务一直"已接收"不动 | 模型凭据问题 | 看 DSH 日志里的鉴权错误；在 DSH 内重新登录 |
| 任务状态"等待批准" | 触发了 DSH 原生审批 | 到 DSH 主界面批准；桥接**故意不代答** |
| 改了代码没反应 | 旧 host 进程还在占端口 | 彻底结束 node/electron 子进程后重启 |
| `git apply` / `patch` 失败 | 不是 git 仓库 / 版本不符 | 改用 `node scripts/patch-dsh-pet.mjs apply`（自带校验与备份） |
| 脚本报"未实测的版本" | dsh-pet 不是 0.4.5 | 装回 0.4.5；确认结构未变再用 `--force` |
| 升级 dsh-pet 后 `/task` 静默失效 | 新版 `index.js` 覆盖，补丁没了 | 重跑 `patch-dsh-pet.mjs apply`；`check` 可先确认状态 |
